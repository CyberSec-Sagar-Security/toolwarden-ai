# Dataset Assembly (Phase 3)

## Sources actually used, and why one locked-decision source was dropped

The [build spec](../ToolWarden_AI_Build_Spec.md)'s locked decisions name PINT, InjecAgent, and AgentDojo as benchmarks. Checking each source directly (repo contents, not memory) before writing any download code turned up a real feasibility problem with one of them:

### PINT — dropped as a trainable/evaluable data source

`lakeraai/pint-benchmark` ships the evaluation methodology (a notebook, category taxonomy, scoring logic) but **not** the actual 4,314-input dataset. Confirmed by listing `benchmark/data/` in the repo directly: it contains only an 8KB `example-dataset.yaml` used to illustrate the input *format*, not real benchmark rows. PINT's own README states the real dataset is "a blend of public and proprietary data" — this is deliberate on Lakera's part, so vendors can't train against it. There is no path to the raw inputs.

**Consequence:** ToolWarden does not train or evaluate on PINT. Where PINT is relevant, it is cited as external context only — e.g. Lakera's own `DETAILS.md` records that the ProtectAI baseline (`protectai/deberta-v3-base-prompt-injection-v2` on HuggingFace) was scored on PINT under specific conditions (threshold 0.5, `SAFE`/`INJECTION` output). That's a citable third-party number, not something ToolWarden reproduces. Any writeup referencing PINT must make this distinction explicit — never imply ToolWarden was run against PINT itself.

### InjecAgent — used as-is, primary in-distribution source

`uiuc-kang-lab/InjecAgent`, MIT licensed, fully public. Real data files confirmed present in `data/`: `attacker_cases_dh.jsonl`, `attacker_cases_ds.jsonl`, `user_cases.jsonl`, `attacker_simulated_responses.json`, `test_cases_{dh,ds}_{base,enhanced}.json`, `tools.json`. 1,054 test cases across 17 user tools and 62 attacker tools, covering direct-harm (`dh`) and data-stealing (`ds`) attack intentions.

### AgentDojo — used as a held-out, structurally-disjoint generalization set

`ethz-spylab/agentdojo` (pip package `agentdojo`), MIT licensed. Not a flat dataset — it's versioned Python task-suite code (97 tasks, 629 security test cases across `default_suites/v1` through `v1_2_2`) that generates agent/tool-call transcripts when *run*, not files you parse.

Phase 3 does a light-touch pass only: install the package, enumerate task suites, and extract static text (task descriptions, injection strings, tool schemas) without running live agent simulations. Full simulation runs are deferred to Phase 8, where live execution against the classifier belongs anyway.

Because AgentDojo is a different paper, different attack-construction methodology, and structurally disjoint from InjecAgent, its extracted text is used as the **held-out novel-attack split** — never touched during training, by construction rather than by a random row-level split of the same source. This is a stronger generalization test than an in-source holdout would be, and it's genuinely leak-proof since the two sources share no authorship or generation pipeline.

## Split design

- **Train / in-distribution test:** InjecAgent data, stratified by attacker-tool category (not row-random) to avoid near-duplicate template leakage between train and test.
- **Held-out novel-attack:** all AgentDojo-derived text. Zero overlap with training by construction — different source, different methodology, never merged into the InjecAgent pool at any stage.

See `datasets/REPORT.md` (generated by `src/toolwarden/datasets/build.py`) for actual sizes, class balance, and a leakage check confirming no text overlap between the train/test pool and the held-out pool.

## Normalized schema

All sources are normalized to one record shape (`src/toolwarden/datasets/schema.py`) before anything downstream (feature engineering, classifier training) touches them, so the pipeline doesn't need to know which benchmark a row came from.
